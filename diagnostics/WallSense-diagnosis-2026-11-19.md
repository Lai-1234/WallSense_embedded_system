## 结论与边界

已确认 Windows 主机端存在明显的读取瓶颈：旧程序使用逐字节的
`Serial.readline()`，与大量 Qt 绘图争用执行时间，无法持续排空串口。
关闭绘图、以及仅将读取换为分块分帧这两项独立测试都显著改善了读取。
本次修复针对这个已证实的瓶颈，以及正常关闭和 CSV 表头问题。

历史数组损坏最可能与主机读取积压及随后的数据丢失有关，但这仍是推断：
本轮原始字节采集与旧 GUI 的短测试均未复现完整记录损坏，没有取得发生
字节丢失时的驱动溢出标志。因此不能宣称已确认历史损坏的最终发生点，
也不能用短期零错误宣称以后永不复发。串口传输余量、无线接收及长期表现
仍有不确定性。没有烧录或修改任何固件、TX 频率或 Wi-Fi 配置。

## 本地代码与设备

- 工作区：`C:/Users/laisi/embedded_system`；代码仓库是 Espressif 的 `esp-csi`，
  `master`，upstream remote 保持不变。开始时没有已暂存修改，只有 TX 天线编辑。
- 使用现有 `.csi-venv/Scripts/python.exe`，没有安装依赖。
- COM7 为 CH343 USB-UART（序列号 `5B5E009622`）；短采集实际收到 C6 CSI 和
  `csi_recv` 增益日志，确认是 RX 输出。
- COM6 为 Espressif USB Serial/JTAG（序列号 `A0:F2:62:78:7D:20`）。历史角色是 TX，
  本次未打开、重置或烧录 COM6，未单凭端口名称断言已重新验证其固件身份。
- TX 在 `csi_send/main/app_main.c` 中使用从 0 递增的 `uint32_t count`，将其作为
  ESP-NOW payload 发送，随后 `usleep(1000 * 1000 / CONFIG_SEND_FREQUENCY)`。
  本地 `CONFIG_SEND_FREQUENCY` 仍为 100；这是名义设置，不代表实测恰好 100 条/秒。
  GPIO3/GPIO14 的原有天线修改保持逐字节不变。
- RX 以 `info->payload + 15` 处的序号作为记录中的序号，而非用回调计数器代替。
  C6 输出实际为 15 字段，含 `fft_gain`、`agc_gain`、长度及 JSON 数组。
- RX 每条记录前输出一条 `ESP_LOGI` 增益日志；CSI 由多次 `ets_printf` 拼接输出。
  这是需要关注的共享输出路径，但本轮未观察到增益日志嵌入 CSI 数组。
- 当前 RX `sdkconfig` 及构建配置一致：UART0，TX GPIO16，RX GPIO17，8N1、921600 baud；
  另启用 USB Serial/JTAG 次要控制台。本次实际数据取自 COM7 的 UART 桥接路径。
  `build/project_description.json` 标识 ESP-IDF v5.5.6、monitor baud 921600。
- 烧录波特率由 idf/esptool 调用参数决定；现有 `flash_args`/`flasher_args.json`
  没有保存一次历史烧录的 `-b` 值，不能由运行时 UART 波特率反推烧录速度。
- 旧 Python 在 QThread 中读取、CSV/JSON 校验、写盘并更新 NumPy 缓冲区；GUI 主线程
  以 100 ms 定时更新大量曲线。独立线程仍可能因逐字节串口调用和绘图竞争而积压。

各次无线采集并非同一批包，所以不能将序号间断数的变化直接解释为无线改善。

本轮新原始记录没有发现缺少分隔符、重复 CSI 前缀、嵌入日志或可确认的拼接数组。

原始基线约 85,232 字节/秒。921600 baud、8N1 的名义容量为 92,160 字节/秒，
本次约占 92.5%，余量不大；这说明后续值得监测传输余量，但不构成本次改固件的证据。

旧 GUI 第一次开端口后，第一条 CSI 的 RX 本地时间戳约为 91,790 微秒，而此前
原始基线约为 1.4×10^9 微秒；该次开端口包含接收端重新启动阶段，也有 85 条

分块读取明显降低积压，不能把每次无线接收数量差异全归因于解析器。

同一份 30 秒原始基线离线重放给**未修改**的旧解析逻辑，得到完全相同的 2,696 条
有效记录，CSV/JSON 错误数为 0（重放处理约 0.397 秒）。这有助于区分纯解析与
实时采集/绘图造成的瓶颈。

## 改动与验证

唯一新修改的项目源文件：`esp-csi/examples/get-started/tools/csi_data_read_parse.py`。

1. 用分块串口读取和保留跨读取片段的换行分帧替换逐字节 `readline()`。
   保留全部校验；超时不被当作行结束。末尾片段明确记录为边界片段。
2. 正确解码字节，先检查字段数再转换长度，并保留非法 CSV、JSON、元数据和数组的
   原文及错误日志，不补值、不截断数组、不默默丢弃坏记录。
3. 按实际记录类型写 CSV 表头；C6 为 15 列。`newline=''` 消除多余空行。
4. 使用有限读取超时和停止事件。关闭窗口时先停绘图、停止并等待工作线程；
   串口在 `finally` 关闭，CSV/log 在上下文退出时刷新并关闭。
5. 保留完整异常 traceback 输出，方便记录再次出现的绘图或读串口异常。

验证：

- 3 项针对性测试通过：任意分块与超时、拒绝且保留异常记录、精确基线重放。
- 修复后 CSV 为 2,742 条有效记录，表头和每行均 15 列、数组均为 256 个整数，空行为 0。
- 30.305 秒内绘图更新 104 次，相位数据变化 103 次；现场观察了相位和 IQ 曲线。
  100 ms 定时设置保留，但实测绘图帧率仍约 3.4 次/秒，不能把定时设置等同于实际帧率。
- 对照测试窗口关闭后，线程运行和串口打开状态均为 false。
- 另用实际脚本入口正常启动并关闭，保存 2,702 条有效记录；退出码 0，随后重新打开
  COM7 成功并关闭，证明无需结束进程来释放串口。
- 本轮没有复现应用的 pyqtgraph traceback。一次诊断包装程序在关闭后的 `flush()`
  操作触发 `ValueError: I/O operation on closed file`；修正包装程序后重测成功。
  这条异常保存在早一轮 `fixed_live.terminal.txt`，不应误归因于 pyqtgraph。
- `git diff --check` 通过；未暂存、提交、推送或构建固件。
